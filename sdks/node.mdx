Use **`@wurk/sdk` 0.7.1** to integrate WURK into a Node.js application. For an agent that can run commands, start with the [CLI quickstart](/quickstart). Both clients support commissioning, worker and seller operations, free account access, and payment recovery.

For an MCP application, start with [Connect with MCP](/sdks/mcp). To connect using your CLI wallet and saved state, follow [Local MCP](/sdks/mcp-local). For scripts that run CLI commands, read [CLI automation](/sdks/cli-automation).

## Install

The SDK is ESM and supports Node `>=22.22.0 <23`, `>=24.12.0 <25`, or `>=26.0.0 <27`.

```bash
npm install --save-exact --ignore-scripts @wurk/sdk@0.7.1
```

SDK-only applications supply an `AccountStore` and, for payments, a durable `PaymentJournalStore`. The example below uses the matching CLI package's SQLite adapters:

```bash
npm install --save-exact --ignore-scripts @wurk/sdk@0.7.1 @wurk/cli@0.7.1
```

The CLI and these adapters support Linux, macOS, and native Windows. On Windows, use private local NTFS storage and follow the installed CLI README's setup; supplied native adapters cover x64 and ARM64. On Linux/macOS, the state directory must be owned and private (`0700`, with `0600` files).

Keep the application lockfile and update both packages together when using the adapters. Stop state writers and back up the complete private state directory before updating. API keys and payment evidence in these stores are unencrypted; keep the directory and backups out of source control.

## Choose storage for your workflow

`createWurkClient` always takes `store`, an `AccountStore`. Add the other stores for the operations your application uses. The matching CLI package supplies these adapters:

| Workflow | SDK configuration | Adapter and import |
| --- | --- | --- |
| Save account access and use its API key | `store` | `SqliteAccountStore` from `@wurk/cli/store` |
| Prepare/pay for work and manage jobs created by that payment journal | `journal` | `SqlitePaymentJournalStore` from `@wurk/cli/journal-store` |
| Create swaps, save withdrawal quotes and confirm them | `financeStore` | `SqliteFinanceStore` from `@wurk/cli/finance-store` |
| Import and manage an existing paid job | `managementStore` | `SqliteManagementStore` from `@wurk/cli/management-store` |
| Receive notifications into a durable processing queue | Pass a `NotificationCollectorStore` to `collectNotificationStream` separately | `SqliteNotificationCollectorStore` from `@wurk/cli/notification-store` |

Keep each store across restarts. The payment journal does not replace finance or imported-job storage. Custom adapters must meet the exported interfaces' atomicity and durability requirements; an in-memory map loses recovery information on restart.

Ordinary profile, worker and seller operations need no payment journal. Finance status/history reads do not require `financeStore`; new swaps, withdrawal quotes and confirmations do. A plain notification stream lets your application handle cursor persistence itself; there is no `notificationStore` option on `createWurkClient`.

Keep original request keys and inputs for mutations even when a method has no dedicated store. For portfolio uploads, preserve the reservation with the SDK's `saveReservation` callback before bytes are sent; follow the [upload recovery guide](/guides/uploads#recover-an-interrupted-portfolio-upload). Profile-picture uploads use the separate direct-upload flow and do not accept that callback.

## Configure your wallet and storage

Supply your application's existing wallet integration. The SDK does not load private keys or choose RPC credentials. Wallet providers **sign only**; they must not broadcast transactions or send paid HTTP requests.

This TypeScript helper configures a Base creator client and closes both stores after your callback. Keep the same directory, origin, and wallet reference across restarts.

```typescript
import {
  createWurkClient,
  type BasePaymentConnection,
  type WalletConnection,
  type WalletRef,
  type WurkClient,
} from '@wurk/sdk';
import type { OperationRef, SpendGrant } from '@wurk/sdk/journal';
import { SqliteAccountStore } from '@wurk/cli/store';
import { SqlitePaymentJournalStore } from '@wurk/cli/journal-store';

export async function withBaseCreator<T>(
  directory: string,
  walletRef: WalletRef,
  authWallet: WalletConnection,
  paymentWallet: BasePaymentConnection,
  run: (client: WurkClient) => Promise<T>,
): Promise<T> {
  if (authWallet.network !== 'base') throw new Error('Expected a Base wallet');
  const store = SqliteAccountStore.open(directory);
  try {
    const journal = SqlitePaymentJournalStore.open(directory);
    try {
      const client = createWurkClient({
        origin: 'https://wurkapi.fun',
        store,
        journal,
        wallets: {
          async resolve(ref) {
            if (ref !== walletRef) throw new Error('Unknown wallet');
            return authWallet;
          },
        },
        paymentWallets: {
          async resolve(ref) {
            if (ref !== walletRef) throw new Error('Unknown wallet');
            return paymentWallet;
          },
        },
      });
      return await run(client);
    } finally {
      journal.close();
    }
  } finally {
    store.close();
  }
}
```

`WalletConnection` supplies `{network, address, signer}` for free message authentication and public wallet identity. `BasePaymentConnection` supplies `{network: 'base', address, signTypedData}` for the same wallet's EIP-712 payment authorization. A viem account can provide `signer` and a `signTypedData: request => signer.signTypedData(request)` adapter. The SDK checks the identity and signature.

For Solana, supply the exported `SolanaPaymentConnection` and a read-only `SolanaPaymentRpc` with `getGenesisHash`, `getLatestBlockhash`, `getFeeForMessage`, and `isBlockhashValid`. The wallet's USDC token account must already exist. Configure a separate SOL fee ceiling if permitting wallet-paid fees.

## Prepare a feedback job

Add this function to the same module. It requests and saves an Advanced USDC quote without paying. Pass the actual public demo URL and a unique request ID for this job; reuse the same arguments for recovery.

```typescript
export async function prepareFeedback(
  client: WurkClient,
  wallet: WalletRef,
  requestId: string,
  demoUrl: string,
) {
  const prepared = await client.commissioning.prepareAdvancedUsdc({
    network: 'base',
    wallet,
    clientRequestId: requestId,
    idempotencyKey: requestId,
    description: `Try the onboarding at ${demoUrl}. Submit one reproducible usability issue, expected behavior, and a suggested improvement. We judge clarity, reproducibility and usefulness.`,
    winners: 2,
    perUser: '1.00',
    selectionType: 'creator',
    selectionTimeMinutes: 1440,
    agentsAllowed: false,
  });
  return prepared;
}
```

Call it inside `withBaseCreator` using your existing wallet providers. Save **`prepared.operation.operation`**, the returned `OperationRef`, outside the callback. An unpaid result normally has `job: null` and safe `checkout` metadata. Inspect `operation.amountAtomic`, `operation.payTo`, the network and asset, and `checkout.initiateBefore` before authorizing payment.

The gross prize budget is 2.00 USDC; each approved winner receives 0.900000 USDC in their platform balance. The payable quote can include an identification amount. Decimal amounts are strings, counts are integers, and audience flags are booleans.

Advanced USDC, Contest, Store, and hire preparation accept **no `access` property**, including `undefined` or `null`. The SDK saves a private checkout token and sends no API key or SIWX login on create/pay requests. Verified payment determines the owner account. The checkout's token and payment-binding metadata stay in the journal.

## Authorize and submit once

The application supplies a `SpendGrant` derived from its approved spending policy. Its fields are:

| Field | Required value |
| --- | --- |
| `id` | Stable allowance ID; preserve it for operations sharing a budget |
| `origin` | The approved API origin, here `https://wurkapi.fun` |
| `wallet` | `{wallet: walletRef, network: 'base', address: paymentWallet.address}` |
| `asset` | `'USDC'` |
| `allowedCapabilities` | `['commissioning:advanced-usdc']` for this job |
| `allowedRecipients` | Recipient addresses approved from the reviewed quote |
| `maxPerOperationAtomic` | Complete payment ceiling as an atomic string; `'2010000'` caps this example at 2.01 USDC |
| `maxTotalAtomic` | Shared allowance ceiling as an atomic string |
| `expiresAt` | Approved UTC expiry in ISO format |
| `solanaFees` | `{mode: 'sponsored-only'}`, or an explicitly approved `{mode: 'bounded', maxLamports: '...'}` |

Authorize only after reviewing the intended work and full quote. The following function uses the approved grant; it does not infer an allowance from whatever price the server returns.

```typescript
export async function payApprovedFeedback(
  client: WurkClient,
  operation: OperationRef,
  approvedGrant: SpendGrant,
) {
  await client.payments.authorize(operation, { grant: approvedGrant });
  return client.payments.submit(operation);
}
```

`authorize` reserves allowance locally without signing or transferring. `submit` signs, preserves the exact payment, and dispatches once. Base checkout signing retains the advertised authorization nonce; Solana signing retains the checkout memo and original transaction evidence. Generic automatic payment wrappers do not replace this persistence and recovery flow.

Read the result's `operation.phase` and `job` fields. Payment confirmation, funding, and job activation are separate. For this Advanced job, wait for `job.fundingStatus: 'funded'` and `job.workStatus: 'open'` before selecting winners.

## Recover and read submissions

After a delay or restart, reopen the same stores and use the saved operation:

```typescript
export async function resumeFeedback(
  client: WurkClient,
  operation: OperationRef,
) {
  return client.payments.resume(operation);
}

export async function readFeedback(
  client: WurkClient,
  operation: OperationRef,
  page = 1,
) {
  return client.commissioning.viewAdvanced({ operation, page, pageSize: 25 });
}

export async function chooseFeedback(
  client: WurkClient,
  operation: OperationRef,
  selectedSubmissionIds: readonly string[],
) {
  return client.commissioning.chooseAdvanced({
    operation,
    submissionIds: selectedSubmissionIds,
  });
}
```

`resume` checks the original checkout and never signs or resends a payment. Honor `retryAfterSeconds` before calling again. Read `view.submissions` and follow `view.pagination.nextPage` while `hasNextPage` is true. Pass actual public submission IDs to `chooseFeedback` after judging their work against the brief.

Selection uses the privately saved job secret and needs no account login. Read `action.status` and `action.result`; completing the required positions queues moderation. After an uncertain selection, reread the view before acting again. See [submissions and winners](/jobs/submissions-winners).

A timeout, `404`, expired quote after submission, or `review` state does not authorize a replacement payment. Keep the original request IDs and state. `payments.inspect(operation)` reads local state; it does not prove the current remote outcome. Follow the [recovery guide](https://wurkapi.fun/references/recovery.md) if local state is missing or the result remains uncertain.

## Free account operations

Account access is a separate, free operation. With the wallet provider configured above:

```typescript
export async function accessAccount(client: WurkClient, wallet: WalletRef) {
  const account = await client.account.access({ network: 'base', wallet });
  const profile = await client.account.profile(account.access);
  return { account, profile };
}
```

Save `account.access`; the account store retains the API key privately. Profile balances are internal WURK balances, separate from the external wallet used for payment. Existing account operations can also use a fresh wallet proof where supported; see [authentication](/authentication).

## Configure finance storage

Use this separate helper for [swaps](/finance/swaps) and [withdrawals](/finance/withdrawals). It opens the saved account and finance stores without making a request. Add it to the same module as the imports above:

```typescript
import type { WalletProvider } from '@wurk/sdk';
import { SqliteFinanceStore } from '@wurk/cli/finance-store';

export async function withFinanceClient<T>(
  directory: string,
  wallets: WalletProvider | undefined,
  run: (client: WurkClient) => Promise<T>,
): Promise<T> {
  const store = SqliteAccountStore.open(directory);
  try {
    const financeStore = SqliteFinanceStore.open(directory);
    try {
      const client = createWurkClient({
        origin: 'https://wurkapi.fun',
        store,
        financeStore,
        ...(wallets ? { wallets } : {}),
      });
      return await run(client);
    } finally {
      financeStore.close();
    }
  } finally {
    store.close();
  }
}
```

For API-key swaps, pass `undefined` for `wallets` and use the saved `AccountAccess`. Wallet-authenticated swaps and all individual withdrawal operations need a provider for the account's registered wallet. These operations use internal balances and free authentication signatures; they do not need `paymentWallets` or an x402 spending grant.

Inside the callback, `client.swaps.create` immediately authorizes a balance reservation. `client.withdrawals.quote` only quotes and saves the terms; review them before explicitly calling `client.withdrawals.confirm` with the same wallet and a persistent idempotency key. Keep this directory when reopening the client to confirm or recover. Without `financeStore`, these methods fail with `FINANCE_STORE_REQUIRED` before sending the operation.

After an uncertain result, read status with the original key before considering a retry. `FINANCE_INTENT_CONFLICT` means saved terms differ: recover the original operation instead of deleting the store. A completed HTTP call can still return a pending swap or withdrawal; inspect the [swap result](/finance/swaps#read-status-until-settled) or [withdrawal result](/finance/withdrawals#3-follow-the-original-withdrawal).
