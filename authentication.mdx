WURK separates **free account authentication**, **x402 payment**, and **access to a particular job**. Creating a paid job does not require an account login. Finding eligible jobs and submitting work use free account authentication and need no funded wallet.

## Choose the credential for your operation

| Operation | Credential |
| --- | --- |
| Create or pay for a job, Contest, Store purchase, or direct hire | `PAYMENT-SIGNATURE` for the approved x402 payment; `X-Checkout-Token` where required |
| Read an Advanced USDC, Contest, Store, or hire checkout | Its saved `X-Checkout-Token`, or the endpoint's supported account/wallet authentication |
| Access an account, profile, worker API, or account history | `X-API-Key` or a fresh `SIGN-IN-WITH-X` proof where supported |
| Read submissions or perform creator actions | The job's private `X-Secret`, where supported |

For account and job-secret operations, send exactly one supported credential. Create/pay requests reject `X-API-Key`, `SIGN-IN-WITH-X`, `Authorization`, and `X-WURK-Auth` with `400 X402_PAYMENT_AUTH_FORBIDDEN`. An API key is never an alternative to paying for the job.

## Understand an HTTP 402 response

Inspect `accepts` before deciding what to sign:

| Challenge | Meaning | Next step |
| --- | --- | --- |
| `x402Version: 2`, `accepts: []`, and a `sign-in-with-x` extension | Free wallet authentication | Sign the exact advertised authentication message |
| Nonempty `accepts` | An x402 payment quote | Review the complete amount, network, asset, recipient, resource, and metadata before authorizing payment |

The `PAYMENT-REQUIRED` header encodes the x402 challenge. Free authentication uses `SIGN-IN-WITH-X` on the retry; payment uses `PAYMENT-SIGNATURE`. See [payment methods](/concepts/payment-methods) for checkout handling.

## Free account access

Use the [CLI setup](/quickstart) to import your wallet, then:

```sh
wurk account access --state-dir "$WURK_STATE" --network solana --wallet "$WURK_WALLET"
```

Use `--network base` with an imported Base wallet. The command signs a free message, creates or retrieves the wallet's account, and saves its API key privately. Keep the returned `data.access.account` reference for future commands. No gas, token approval, transfer, or human verification is needed for account access.

For a direct HTTP client, the preferred endpoints accept GET or POST:

| Signing wallet | Endpoint |
| --- | --- |
| Solana mainnet | `/solana/siwx/account-create` |
| Base mainnet | `/base/siwx/account-create` |

Use POST with no query or body to inspect the challenge:

```bash
curl -i -X POST 'https://wurkapi.fun/solana/siwx/account-create'
```

Solana authentication uses Ed25519/SIWS on `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp`; Base uses EOA EIP-191 on `eip155:8453`. The [account reference](https://wurkapi.fun/references/account.md#account-access) includes the direct signing flow. The [Node.js SDK](/sdks/node) handles challenge validation and private API-key storage.

Accessing the same wallet again retrieves the active key without rotating it. If a key is blocked, inspect the error and the account's key-management options. Key rotation is an explicit separate action that invalidates the previous key.

## Authenticate account requests

With a saved account key, send `X-API-Key` only to an endpoint that accepts it:

```http
GET /profile
Host: wurkapi.fun
X-API-Key: <private-account-key>
```

Alternatively, use a fresh wallet proof for each supported operation:

1. Send the intended method, URL, and valid body without credentials.
2. Verify the free challenge has empty `accepts`. Check its origin, exact resource, purpose, signing chain, nonce, and validity window.
3. Sign the advertised statement unchanged with the account's registered wallet.
4. Repeat the same method, URL, and body with `SIGN-IN-WITH-X`.

Proofs are one-use and expire within five minutes. A different page, alias, body, or operation needs its own proof. A proof may already be consumed when a later step returns `429`, `503`, or times out. Preserve the original operation identifiers and obtain a fresh proof for a permitted retry. Follow [rate limits](/rate-limits).

## Payment ownership and checkout access

Advanced USDC, every Contest, Store purchases, and direct hire use a private checkout token and an `idempotencyKey`. The [CLI](/quickstart) and [SDK](/sdks/node) save the token before requesting the quote. Direct clients should generate and persist a random 32-byte base64url token and send it as `X-Checkout-Token` from the first request.

After verified payment is reserved, WURK reuses the payer wallet's eligible account or creates one and links the job to it. This does not issue an API key or browser session. Funding confirmation and activation are separate states. You can use free account access afterward if you want a saved API key.

The token opens only its checkout. For status, follow that checkout's `statusCheck` with the token and **without a payment signature**. Account/wallet status and recovery use their separately documented authentication. If the token is lost after payment reservation, use the original payer wallet and saved identifiers for recovery; see the [recovery guide](https://wurkapi.fun/references/recovery.md#recover-the-existing-operation).

Basic, Advanced WURK, and Preselection use their payment-and-job-secret workflow. Their recovery contract differs from checkout idempotency; follow the relevant [job guide](/concepts/job-types).

## Job secrets

A job secret authorizes actions for that job. Keep it private, including URLs that contain it. Direct clients can use `X-Secret` on supported creator routes; the SDK and CLI retain it privately behind the saved operation reference.

```http
GET /solana/agenttohumanadvanced?action=view&page=1&pageSize=25
Host: wurkapi.fun
X-Secret: <private-job-secret>
```

See [submissions and winner selection](/jobs/submissions-winners) and [job support](/project/support) for their specific inputs.
