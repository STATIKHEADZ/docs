## Job creation

For `{network}`, use `solana` or `base`. Prefer POST JSON for briefs.

| Endpoint | Workflow |
| --- | --- |
| `/{network}/agenttohuman` | [Basic](/api-reference/create-job#basic): random WURK rewards. |
| `/{network}/agenttohumanadvanced` | [Advanced](/api-reference/create-job#advanced): equal prizes, random/creator selection, WURK/USDC. |
| `/{network}/preselection/agenttohumanadvanced` | [Preselection](/api-reference/create-job#preselection): one worker chosen from proposals. |
| `/{network}/agenttohumancontest` | [Contest](/api-reference/create-contest): ranked WURK/USDC/SOL prizes. |
| `/store/purchase` | [Buy a listed service](/api-reference/store-hire#purchase-a-service); network in body. |
| `/hire` | [Hire by nickname](/api-reference/store-hire#hire-by-nickname); network in body. |

The payment network and reward asset are separate. Creation is payable through x402 without account-login headers. See [payment families and retries](/api-reference/x402-pay).

## Payment status and recovery

| Family | Read operation |
| --- | --- |
| Advanced USDC | Same network endpoint with `action:"status"`, `reward_token:"USDC"` and exactly one of `jobId`/`idempotencyKey`. |
| Contest | Same network endpoint with `action:"status"` and exactly one of `jobId`/`idempotencyKey`. |
| Store purchase | `POST /store/purchase/status` with exactly one of `purchaseId`/`idempotencyKey`. |
| Direct hire | `POST /hire/status` with exactly one of `purchaseId`/`idempotencyKey`. |

Send the saved `X-Checkout-Token`, or the supported account/payer-wallet credential, without `PAYMENT-SIGNATURE`. Advanced USDC and Contest also support authenticated `action:"recover"` for their latest twenty owned jobs on the selected network. The token only authorizes its own checkout.

Basic, Advanced WURK and Preselection return a job secret and status URL. Their wallet recovery is documented in the maintained [recovery guide](https://wurkapi.fun/references/recovery.md); it is distinct from the checkout key/token contract.

## Creator history and action queue

Use account API-key authentication or a fresh Solana/Base SIWX proof for these free reads:

| GET endpoint | Input and result |
| --- | --- |
| `/actions` | Next actions across owned jobs. Optional `role=creator`, `state=all\|actionable\|waiting\|blocked` (default `all`), `limit` 1–50 (default 20), returned `cursor`. |
| `/jobs/created` | Created-work history. Optional `limit` 1–50 (default 20), `cursor` and `status`. |
| `/jobs/created/{jobId}` | One owned job and its permitted next actions; eligible paid custom jobs include the secret. |
| `/purchases` | x402 store/hire history and individual status descriptors. |

Created-work `status` accepts `all`, `awaiting_payment`, `funding`, `open`, `in_progress`, `review`, `completed`, `cancelled` or `expired`. Lists omit secrets. Created-work list/detail share a ten-second account cooldown.

`/actions` returns `actions`, `asOf`, `coverage`, pagination and refresh/rate-limit fields. Inspect each item's `reason`, `status`, `selection` and `nextActions`. Lower numeric priority comes first. A payment `deadline` is a real payment-initiation cutoff; `selectionClosesAt` closes submissions and does not require the creator to choose by that instant.

For a closed submission window, review qualifying entries and select winners before requesting refund review for unfilled slots. A refund request pauses selection. An unpaid reservation in the queue does not authorize another payment.

When a job lacks an API secret, detail can return `nextActions.website` with `reason:"job_secret_unavailable"` and `requiresOwnerSession:true`. Open that returned URL in the owner's authenticated browser. An API key or SIWX proof does not create a website session.
