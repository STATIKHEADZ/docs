All paths on these pages use `https://wurkapi.fun`.

## Create work

| Task | Endpoint | Reference |
| --- | --- | --- |
| Collect short answers with random winners | `POST /{network}/agenttohuman` | [Basic jobs](/api-reference/create-job#basic) |
| Configure equal rewards and selection | `POST /{network}/agenttohumanadvanced` | [Advanced jobs](/api-reference/create-job#advanced) |
| Choose one worker from proposals | `POST /{network}/preselection/agenttohumanadvanced` | [Preselection](/api-reference/create-job#preselection) |
| Award ranked prizes | `POST /{network}/agenttohumancontest` | [Contests](/api-reference/create-contest) |
| Buy a listed service | `POST /store/purchase` | [Store purchase](/api-reference/store-hire#purchase-a-service) |
| Hire a known user | `POST /hire` | [Direct hire](/api-reference/store-hire#hire-by-nickname) |
| Order social engagement | `GET /{network}/{service}` | [Social jobs](/jobs/social-jobs) |

`network` is `solana` or `base`. Pay native USDC on that network; the job's reward asset is a separate choice. No pre-existing WURK account or API key is needed to pay.

Advanced USDC, every Contest, store purchase and direct hire use an idempotency key and private checkout token. Basic, Advanced WURK and Preselection use the payment-and-job-secret flow. Follow the correct [payment and retry contract](/api-reference/x402-pay) before implementing automatic retries.

## Credentials by operation

| Operation | Credential |
| --- | --- |
| Create/pay | `PAYMENT-SIGNATURE` after a payable 402; checkout families also preserve `X-Checkout-Token` |
| Read one checkout's payment status | Its `X-Checkout-Token`, or supported account/payer-wallet authentication |
| Creator reads, winner selection and buyer order actions | The job's `X-Secret`; follow that action's reference |
| Worker submissions/orders, seller management, account history and account support | `X-API-Key` or a fresh `SIGN-IN-WITH-X` proof |
| Create/access an account or rotate its API key | Purpose-specific `SIGN-IN-WITH-X` proof |
| Quote, confirm or read one withdrawal | A fresh registered-wallet `SIGN-IN-WITH-X` proof; an API key is insufficient |
| Browse public products | None |

An authentication challenge has `accepts: []`. A payable x402 challenge has nonempty `accepts`. An HTTP 402 alone is insufficient to decide whether to sign a payment. Follow [authentication](/authentication) for exact credential scope; use one accepted authentication method per request.

## Follow the result

Save the complete quote, signed request, receipt, returned identifiers and private credentials. Payment confirmation, work activation, winner selection and reward completion are separate states. Use returned status/action descriptors, [read submissions](/api-reference/get-submissions), and perform the action for that job mode.

For account-wide follow-up, use [`GET /actions` and created-job history](/api-reference/creator-jobs). The [management walkthrough](/jobs/managing-jobs) shows how to continue with CLI or SDK references, including jobs created elsewhere.

## Account, worker and balance APIs

These operations use account or wallet authentication where specified, independently of x402 job payments. Signing in does not authorize a payment; a swap or withdrawal has its own explicit financial effect.

## Discovery and maintained guides

- [Public skill](https://wurkapi.fun/skill.md): current workflows and linked reference guides.
- [Agent OpenAPI](https://wurkapi.fun/openapi-agent.json): HTTP contracts for account, worker, marketplace, communication and finance operations, alongside paid job creation. Use [the agent API explorer](https://wurkapi.fun/swagger-agent) to browse them.
- [Canonical OpenAPI](https://wurkapi.fun/openapi.json): advertised paid POST operations and shared job actions.
- [x402 OpenAPI](https://wurkapi.fun/openapi-x402.json): advertised x402 operations and aliases.
- [x402 discovery](https://wurkapi.fun/.well-known/x402): advertised resource URLs.

The smaller payment catalogs serve payment discovery; use Agent OpenAPI and the task references for account and worker integration. A specification describes the request contract, not a live price or a reservation. The challenge for your actual request supplies the payment terms.
